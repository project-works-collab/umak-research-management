# IAS implementation and operation

Updated 10 November 2026 (Asia/Manila). These changes are local workspace work, not a deployed university service or remote CI result. The original planning document is [here](plans/IAS_CIA_IMPLEMENTATION_PLAN.md).

## Implemented

* **Confidentiality:** PostgreSQL FORCE RLS on studies, membership, assignments, profiles, feedback, internal notes, document metadata, consultation tickets, consent and deletion requests. Transaction-local identity follows the authenticated database-backed JWT session across pooled connections. Student and faculty researchers have scoped access; CRM staff access private studies only when assigned. Explicitly Approved catalogue metadata remains public, including its abstract; approval must therefore mean permission to publish those catalogue fields. Manuscripts stay private.
* **Feedback:** researcher-visible feedback and internal staff notes have separate tables and policies. Researcher response projections never contain the internal column. Study owners can add/remove researcher members; reviewer assignment is an operator-controlled operation, with no staff self-assignment endpoint.
* **Credentials:** asynchronous Argon2id (19 MiB, t=2, p=1), random salts, bounded expensive-operation concurrency, exact legacy scrypt verification and upgrade on successful login. HS256 JWT bearer tokens expire after 15 minutes and are checked against database sessions on every authenticated request, preserving logout/deletion revocation. Algorithm, issuer, audience, signature, subject and lifetime are validated; roles come from the database. No persistent refresh flow is provided. Staff can issue single-use 15-minute activation tokens; only their SHA-256 digest is stored. High-entropy activation tokens use token hashing; the chosen human password uses Argon2id.
* **Integrity:** strict Zod contracts, parameterized SQL, database-triggered transactional `audit_history` with actor, target, old/new metadata, timestamp, request ID and IP. Runtime cannot insert/update/delete history. Passwords, manuscript abstracts, feedback content, internal note contents and object keys are excluded from audit payloads. Document fingerprints are retained from migration 007 onward. Existing `audit_logs` are retained as legacy events. Migration 007 adds SHA-256 hash chaining and verification; database owners remain able to rewrite the entire chain/head, so external trusted checkpoints are still an operational requirement.
* **Documents:** bounded raw uploads (25,000,000 bytes), two active uploads per API process, isolated parser workers with heap/time limits, PDF parsing, bounded DOCX ZIP/XML inspection, fail-closed ClamAV scanning, fresh object keys, SHA-256 integrity metadata, numbered document revision series, private S3 adapter and authorized 600-second GET URLs. Nothing is placed in cloud storage until validation and scanning pass. Upload failure cleans its object when possible; an orphan-cleanup failure produces an operator log. The deployment must monitor that log. Per-worker concurrency plus shared upload token buckets bounds admission; a fleet-wide scanner concurrency lease is not implemented.
* **Availability:** PostgreSQL-backed atomic token buckets and a separate rolling five-failed-attempts/15-minute account/IP limiter shared across API instances. In-flight login reservations count conservatively; successful attempts remove their own reservations. Unknown-user passwords take the expensive dummy verification path. Dependency failures are sanitized; failures of the limiter store return controlled 503 responses. Health is a lightweight process liveness probe, not a database readiness guarantee.
* **Recovery:** encrypted AES-256-GCM database/object snapshot archives, a separate offsite destination, freshness checker, quarantined restore drill, object-deletion queue, independent encrypted deletion-event export/replay and Linux systemd deployment units. The dump and document inventory use one exported PostgreSQL snapshot. Restores verify archived object checksums; they do not publish recovered objects automatically. Deletion events use immutable UUID subject references. Export runs on a proposed five-minute timer, so an unexported deletion can be absent after a disaster; restore quarantine and operator reconciliation remain required.
* **Android app and library:** Room public-information cache, app-private template files, checksum validation, atomic cache publication, WorkManager refresh, Android Keystore AES-256-GCM session vault and instrumentation tests. No deprecated EncryptedSharedPreferences dependency. The launchable `:app` module integrates sign-in, logout, Keystore session storage, Room resource listing, refresh scheduling, stale/empty states and saved plain-text blank-form viewing. It does not yet provide research submission/review screens. Public catalogue/form contents are explicitly synthetic placeholders.

## Run and migration

Use Node 24 and PostgreSQL 18. Install with `npm ci --ignore-scripts`. On an existing installation, run `npm run db:migrate` using the privileged migration identity, then restart the API. New synthetic installations use the README setup sequence. Migration functions require a trusted owner that bypasses FORCE RLS (the tested setup/restore owner is PostgreSQL superuser `postgres`); never run the API with that identity. The migration identity owns protected functions with fixed search paths and restricted EXECUTE grants.

Migrations preserve existing author IDs and backfill ownership membership. They **do not** assign every existing staff member to every study. Provision reviewer mappings through the privileged operator connection using parameterized `INSERT INTO review_assignments(study_id,staff_id) VALUES($1,$2)` after verifying that the target account is CRM staff. `db:setup` adds explicit reviewer assignments only for its three synthetic studies, refreshes demo password hashes, and clears synthetic throttling counters; it is not a production migration command.

New routes:

| Route | Access / body |
| --- | --- |
| GET/PATCH `/api/v1/users/me` | Own profile; PATCH accepts email only |
| PATCH `/api/v1/research/:id` | Research member; title and optional abstract/year/department |
| POST `/api/v1/research/:id/members` | Owner; `{user_id}` for a student/faculty account |
| DELETE `/api/v1/research/:id/members/:memberId` | Owner; cannot remove self |
| GET `/api/v1/research/:id/feedback` | Member or assigned staff; researcher projection omits notes |
| PUT `/api/v1/research/:id/feedback` | Assigned staff; both `researcher_visible_feedback` and `internal_staff_notes` |
| POST `/api/v1/research/:studyId/documents?filename=study.pdf` | Member researcher; `Content-Type: application/octet-stream`, raw file bytes |
| GET `/api/v1/research/:studyId/documents/:documentId/url` | Member or assigned staff; temporary private URL |
| POST `/api/v1/admin/invitations` | Staff; `{email,role:"student"\|"faculty"}`; returns activation token once |
| POST `/api/v1/auth/activate` | `{token,password}`; password 12–128 characters; no automatic sign-in |
| GET `/api/v1/admin/audit-history` | Staff, last 100 metadata events |
| GET `/api/v1/public/content` | Synthetic published directory/requirements/instructions/template manifest, ETag |
| GET `/api/v1/public/templates/research-request.txt` | Blank synthetic form; never contains applicant data |

Role/ownership scope is enforced again in the database. The public search function exposes only approved catalogue columns through a narrowly granted function. Server-controlled transaction context is defense against omitted predicates, not protection against a fully compromised server or stolen privileged DB credential.

## Switch on deployment controls

1. Configure a private manuscript bucket with `ops/private-storage.yaml`; attach its least-privilege managed policy to the API workload identity. Use `S3_BUCKET`, `AWS_REGION` and the standard AWS credential chain. Prefer workload credentials over embedded keys. The S3 adapter supports an HTTPS custom endpoint for R2, but R2 requires its own provider policy, checksum/encryption and signed-URL verification; it was not deployed here.
2. Start ClamAV with StreamMaxLength at least 25,000,000 bytes and a scan timeout compatible with the API's 30-second scanner deadline. Set `CLAMAV_HOST`/`CLAMAV_PORT`. Without storage or scanner configuration uploads return 503. Place upload/scan services within the same protected trust boundary; the implemented ClamAV TCP protocol is not itself encrypted/authenticated. Production segmentation or a mutually authenticated transport wrapper is a deployment requirement.
3. Supply `TLS_CERT_FILE`, `TLS_KEY_FILE`, `DB_TLS_CA_FILE` and `NODE_ENV=production`. API ingress and runtime DB connections require TLS 1.3 and certificate verification. Configure database volume AES-256 encryption in the hosting platform; this source tree cannot encrypt a running cloud database volume. Verify actual protocols and encryption metadata after deployment. No `trust proxy` is enabled: the current limit/IP behavior uses the direct peer. A reverse-proxy deployment needs a narrowly scoped trust configuration and spoofing tests before launch.
4. Deploy `ops/offsite-storage.yaml` in a separate recovery account/region with independently governed permissions. API credentials must have no recovery access. Backup jobs need source DB/document read access plus destination write access; restore jobs need independent read credentials. The supplied policies are attachment templates, not automatic cross-account role assumption. Create the cross-account trust/grants explicitly. Keep `BACKUP_KEY_FILE` (0600, 64 hex characters from 32 CSPRNG bytes) outside backups and maintain separately governed recovery copies. AES encryption with a lost key is unrecoverable.
5. Install systemd units from `ops/` only on the intended Linux deployment. Create `/etc/crm/backup.env` (0600), `/var/lib/crm-backup` and service identity `crm-backup`; adapt `/opt/crm` and Node binary paths. Backup timer: daily 02:00 Asia/Manila; restore timer: monthly day 1 at 03:00; deletion export: every five minutes. Units are supplied **but not installed/enabled on this Mac**. Alert unit writes an operator journal/syslog event; connect the deployment monitoring system to failed units and enable the supplied `crm-backup-freshness.timer` for hourly checks. No external notifications were sent.
6. Approve retention for logs, old S3 object versions, backups and deletion ledgers before adding lifecycle expiry/Object Lock. Versioning is enabled by templates; no immutable-retention or permanent-erasure claim is made. S3 DeleteObject creates a delete marker in a versioned bucket; old versions require that approved lifecycle/sanitization procedure. Independent deletion events must outlive recoverable backups. Quarantined drills never reopen public service automatically.

Scripts: `npm run backup:offsite`, `npm run backup:restore:encrypted`, `npm run backup:freshness`, and `npm run privacy:maintain`. `BACKUP_STATUS_FILE` records the last successful upload; freshness fails on missing/stale/non-offsite evidence. For a synthetic local exercise only, use `BACKUP_LOCAL_DIR` and restore with `BACKUP_ARCHIVE_FILE`. These modes are not offsite evidence. Backup/maintenance administrative connections and pg_dump must be configured with verified production TLS through the supplied environment/connection settings; the local evidence uses isolated loopback/socket connections.

## JWT and Android integration (10 November 2026)

Set `JWT_SIGNING_KEY` to 32–64 cryptographically random bytes encoded as lowercase hex (for example, `openssl rand -hex 32`). Store it in the deployment secret manager and share it across API replicas. Production refuses missing/malformed keys. Development without a key uses a process-local random key; restart signs everyone out. Existing opaque sessions are rejected after this change, so clients must sign in again. Rotation also requires sign-in. No database migration is needed: only the SHA-256 digest of the signed token is stored in the existing session table.

Build the Android launcher with `cd android-public-cache && ./gradlew :app:assembleDebug`. Enter the deployed HTTPS origin, then sign in or refresh public resources. Tokens are encrypted by the existing Android Keystore vault, bound to their server origin, and cleared locally on expiry/logout. Online logout also revokes the database session. Offline logout clears the device secret and reports that server revocation could not complete. Public data and blank forms remain available after logout; private manuscripts and feedback are not cached. This minimal app implements these CIA workflows, rather than a complete research-management frontend.

On the configured Linux deployment, run `sudo sh ops/install-recovery-timers.sh` to install and enable daily backups, monthly restore drills, five-minute deletion-event exports and hourly freshness checks. It checks required deployment paths, service identity and PostgreSQL tools first. The installer does not provision cloud accounts, credentials, bucket policies, certificates or monitoring integrations. It has not been executed on this Mac.

Verification for this change: the three standalone JWT tests passed (expiry, tampering, wrong signing key, issuer/audience/lifetime/subject validation, algorithm rejection and production configuration). Database integration, Android compilation/device tests, cloud configuration and Linux timer activation remain unverified. The security skill requires a fully bounded sandbox for target-controlled builds; this host lacks a configured complete resource-limited Android build sandbox. Run the Android build/device checks in an appropriately isolated CI or development environment before release.

JWT validation follows [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), including fixed algorithm and intended issuer/audience checks.

## Audit chains, lifecycle and document revisions (10 November 2026)

Apply migration `007_integrity_lifecycle_versions.sql` with `npm run db:migrate` before restarting the changed API. The migration locks audit history while backfilling its existing entries, so schedule it during a maintenance window. Existing studies start at `Registered`; approval does not imply defense completion. Existing files each start their own document series at revision 1; unrelated historical uploads are not guessed to be revisions.

* **Audit chain:** each audit-history insertion acquires the protected singleton head row, assigns a consecutive chain index and stores the previous hash plus a SHA-256 digest over an explicit, versioned JSONB field set. Timestamp serialization uses UTC. The head update and event insertion commit or roll back together. Runtime permissions continue to deny audit mutation and access to the head table. Existing history is chained as it exists at migration time; this cannot prove its authenticity before migration. Future document events retain SHA-256 content fingerprints, revision numbers and predecessor IDs; private manuscript content, object keys, notes and passwords remain excluded.
* **Verification:** staff can call `GET /api/v1/admin/audit-history/verify`, receiving `valid`, `entries`, `first_invalid` and `head_hash`. Verification detects changed entries, broken links, sequence gaps and removal of the tail relative to the protected head. History responses include `chain_index`, `previous_hash` and `entry_hash`. An owner capable of rewriting both the history and its protected head can rebuild the chain; separately retained trusted checkpoints are required to detect a complete privileged rewrite. A hash chain is tamper-evident, not immutable storage. Verification scans the full log; use it operationally rather than polling from every client.
* **Lifecycle:** authorized team members and assigned officers can read `GET /api/v1/research/:id/lifecycle`. Assigned CRM officers append events using `POST /api/v1/research/:id/lifecycle/events` with `{ "event": "UnderReview", "occurred_at": "2026-11-10", "expected_version": 2 }`. Allowed progress: Registered → In-Progress → UnderReview → Completed; UnderReview may return to In-Progress. `Presented` and `Published` independently set their own dates, even before completion. Outcome duplicates, invalid transitions and stale versions return 409. Dates must be real calendar dates and cannot be in the future in Asia/Manila. Occurrence dates may be entered after the event; dates are returned as YYYY-MM-DD without timezone conversion. Ordinary researcher UPDATE grants cannot bypass transitions. Approval/public catalogue visibility remains separate. Correction/reversal of a completed outcome requires an institutional policy and an audited operator migration; no silent overwrite endpoint is supplied.
* **Revisions:** upload a new independent document as before. For its next revision, add `previous_document_id=<latest-document-uuid>` to the existing upload query. The database allocates the series and revision number, retains every earlier object and fingerprint, and rejects stale predecessors with 409. The study row lock and unique predecessor/series constraints serialize competing revisions. A rejected metadata insert removes its newly uploaded object, with the existing operator warning if cleanup fails. `GET /api/v1/research/:studyId/documents` lists authorized revision metadata. Each revision keeps its own ID, so the existing `/:documentId/url` route downloads any retained revision through a fresh temporary URL. Revision metadata is read-only for runtime users; normal approved privacy deletion still removes a study and its associated documents.

The new database integration suite is `npm run test:integrity:db`. Run only after migrations on an isolated disposable synthetic database with `ALLOW_SYNTHETIC_SETUP=yes`, `DATABASE_URL` and `ADMIN_DATABASE_URL`. It covers transition/role/version enforcement, independent outcomes, revision lineage/stale writes, fingerprint retention, privileged tampering and tail deletion inside rolled-back fixtures, and chain rollback consistency. The suite is added but has not been executed here: the [security-audit skill](../.agents/skills/security-audit/SKILL.md) requires “explicit low CPU, memory, process, file-size, disk, and wall-clock limits” for target-controlled execution, and a complete database-test sandbox is unavailable on this host. JavaScript syntax and whitespace checks pass. These are source changes awaiting integration validation, not deployment evidence.

These changes and the CIA changes belong in one branch/commit. The unrelated `benchmarks/colab/` work is not part of this security/lifecycle change.
